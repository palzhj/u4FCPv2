# u4FCP v2 - DDR4 self-test (SiTCP)

Self-test firmware for the **two DDR4 SODIMM sockets** of the u4FCP v2 board.
The design is a copy of the `sitcp` project extended with

* two independent `ddr4` MIG controllers (64-bit, **non-ECC** SODIMMs),
* a hardware memory test engine per controller (write pass + read-back pass),
* an RBCP register interface so the test can be started and its result read
  over Ethernet (SiTCP), and
* a behavioural simulation of the test engine.

The bit stream keeps the SiTCP / register-file / I2C / UART functionality of the
original project, so the board can be identified and controlled as before.

## Hardware configuration

| Item              | Value                                                      |
| ----------------- | ---------------------------------------------------------- |
| FPGA              | XCKU15P-FFVE1517-2-E (Kintex UltraScale+)                   |
| Memory part       | MTA16ATF2G64HZ-2G3 (16 GB, 2 ranks, 64-bit, non-ECC SODIMM) |
| Controllers       | 2 (socket A = `C0_DDR4_*`, socket B = `C1_DDR4_*`)          |
| MIG user clock    | 250 MHz (`ui_clk`), 4:1 PHY ratio, 512-bit APP data         |
| APP address range | 16 GB, `app_addr` unit = 8 bytes, one beat = 64 bytes       |
| Reference clock   | 125 MHz from `CLK_IN_PL` (PLL1 out1)                        |

Both MIG instances are configured with **`System_Clock = No Buffer`**: a single
`IBUFDS` + `BUFG` in `top.v` buffers `CLK_IN_PL` and feeds both controllers.
This is required because the MIG PHY instantiates its own input buffer in the
"differential" mode, and two input buffers cannot be placed on the same pin
pair.

The DDR4 pin/IO-standard constraints are in
`constraints/u4fcpv2_top.xdc` (sections *DDR4 A* / *DDR4 B*).

## Building

Vivado 2022.2 (the MIG IP files are generated by the script, no manual IP
customisation is needed).

```tcl
cd scripts
source ./create_project.tcl
source ./run_implementation.tcl
```

Output files are copied to `output/` (`top.bit`, `top.ltx`, `top.mcs`,
`top.prm`). `create_project.tcl` runs the out-of-context synthesis of every IP
(including the two DDR4 MIGs) and waits for all of them, `run_implementation.tcl`
then only resets and runs the top level synthesis and implementation.

## Register map

The DDR4 self-test register file is the **user wishbone device 0x0005** of the
RBCP address space (see `RBCP_REG.v`). Each controller owns a 64-byte block:

| Controller | RBCP base address |
| ---------- | ----------------- |
| socket A (C0) | `0x0005_0000`  |
| socket B (C1) | `0x0005_0040`  |

Offsets relative to the base:

| Offset | Name      | Access | Description |
| ------ | --------- | ------ | ----------- |
| `0x00` | CTRL      | W      | `[0]` start (write 1), `[1]` abort (write 1), `[3:2]` pattern |
| `0x01` | STA       | R      | `[0]` calibration done, `[1]` busy, `[2]` pass, `[3]` fail, `[6:4]` phase, `[7]` done |
| `0x02` | ERR_LANE  | R      | lowest failing 64-bit lane of the first error |
| `0x03` | LIMIT_MB  | R/W    | sweep length in MB `[7:0]`, 0 or >= 16384 = whole memory |
| `0x04` | LIMIT_MB  | R/W    | sweep length in MB `[15:8]` |
| `0x05` | ERR_CNT   | R      | number of failing 64-byte words (32-bit, little endian) |
| `0x09` | ERR_ADDR  | R      | APP address of the first error (32-bit, unit = 8 bytes) |
| `0x0D` | CUR_ADDR  | R      | current sweep address (progress, unit = 8 bytes) |
| `0x11` | EXP_DATA  | R      | expected 64-bit lane of the first error |
| `0x19` | RD_DATA   | R      | read-back 64-bit lane of the first error |
| `0x3F` | ID        | R      | `0xD4` when this firmware is loaded |

`STA` phase encoding: `0` idle, `1` write pass, `2` drain, `3` read/compare
pass, `4` finished.

The register file is in the 125 MHz housekeeping clock domain; the test engine
runs in the 250 MHz MIG `ui_clk` domain. Control bits are passed as toggles and
the status is transferred through a request/acknowledge mailbox, sampled every
1024 clock cycles (~8 us), so `CUR_ADDR` is a live progress indicator.

## Test algorithm

For every controller independently:

1. **Write pass** - for every 64-byte word of the selected address range an
   address-dependent pattern is written (data is presented before the command,
   the command is only issued once the data was accepted).
2. **Drain** - 2048 `ui_clk` cycles (~8 us) pause so the controller can flush
   the write FIFO.
3. **Read pass** - the range is read back in the same order and compared with
   the expected pattern. Because the controller returns read data in request
   order, the expected address is simply counted up.
4. Errors are counted; the first error latches the address, the lowest failing
   64-bit lane and both data values. The run ends in phase 4 with `pass` set
   when no error was seen.

Patterns (`CTRL[3:2]`):

| Value | Pattern | Description |
| ----- | ------- | ----------- |
| `0` | address random | 512-bit word built from `xorshift64(app_addr)`; catches address decoding faults (rank, bank group, bank, row, column) because the expected data depends on every address bit |
| `1` | walking one | one bit set, rotating with the address; catches stuck-at and shorts |
| `2` | walking zero | inverse of `1` |
| `3` | checker board | `0x5A`/`0xA5` bytes, different per lane and address; catches coupling |

Timing: the write pass runs at ~1 word per 2 `ui_clk` cycles, the read pass at
the controller's read rate. A full 16 GB sweep takes a few seconds
(write + read of 32 GB at ~2 GB/s per controller).

Both controllers can run at the same time (separate `start` bits).

## Programming the FPGA

`scripts/program_fpga.sh` downloads a bit file to the FPGA over JTAG using
Vivado in batch mode (no GUI). The JTAG clock is set to **10 MHz** by default;
cables that do not support a programmable clock keep their default and the
script prints a warning.

```bash
cd scripts

# output/top.bit at 10 MHz, local hw_server
./program_fpga.sh

# explicit bit file, 5 MHz
./program_fpga.sh ../output/top.bit 5000000

# remote hw_server
./program_fpga.sh ../output/top.bit 10000000 192.168.10.50:3121
```

The script starts/adopts a local `hw_server` (`localhost:3121`), filters the
XCKU15P out of the JTAG chain (an attached FMC card may add devices), programs
the FPGA and loads the `.ltx` probes file when it exists next to the bit file.
Programming the configuration flash (`top.mcs`) is *not* part of this script.

Equivalent direct call:

```bash
vivado -mode batch -nojournal -nolog -notrace -source program_fpga.tcl \
       -tclargs ../output/top.bit 10000000 localhost:3121
```

## Running the test

`scripts/ddr4_selftest.py` is a small standalone host tool (it only needs
Python 3 and, optionally, the `u4FCPv2` driver package: when the package is not
installed it falls back to its built-in RBCP implementation).

```bash
# read the status of both sockets
python3 scripts/ddr4_selftest.py status

# run the address-random pattern over the first 64 MB of both sockets
python3 scripts/ddr4_selftest.py run --ctrl both --pattern 0 --limit-mb 64

# full memory sweep of socket B with the walking-one pattern
python3 scripts/ddr4_selftest.py run --ctrl 1 --pattern 1 --limit-mb 0
```

The tool waits for calibration, starts the run, polls until the engine reports
`done` and prints pass/fail, the error count and the first error address
(byte address = `ERR_ADDR * 8`). Example:

```
C0 (0x0005_0000): calibration OK, idle
C1 (0x0005_0040): calibration OK, idle
C0: running (phase 3, 12.0 MB of 64.0 MB)
C0: PASS  (0 errors)
C1: PASS  (0 errors)
```

A failing memory report looks like:

```
C1: FAIL  152 errors, first error at byte address 0x0000_1A40 (lane 3):
           expected 0x...1234, read 0x...1230
```

If `STA[0]` (calibration) stays 0, the controller did not calibrate: check the
DIMM, the 1.2 V supply and that `CLK_IN_PL` (125 MHz from the Si5345) is
running. A write of `CTRL[1]` (abort) stops a running test; the DDR4 reset
trigger of the register file (`RBCP 0x0000_0005` = `sys_rst`, bit 1) restarts
calibration for both controllers.

## Timing / clocking notes

* `CLK_IN_PL` (125 MHz) is buffered once (`IBUFDS` + `BUFG`) and both MIGs use
  `System_Clock = No Buffer`, so one input buffer serves both controllers. The
  `CLOCK_DEDICATED_ROUTE BACKBONE` constraint on that net tells Vivado to route
  the shared clock to the two MIG MMCMs, which are placed in two different
  clock regions.
* The register file (`clk_out3_clk_wiz`, 125 MHz) and the two MIG user clocks
  (`mmcm_clkout0`, `mmcm_clkout0_1`, 250 MHz) are asynchronous domains. The
  crossing logic uses 2-FF synchronizers and a toggle/mailbox handshake, so
  `constraints/ddr4_timing.xdc` declares the three domains asynchronous. That
  file is an implementation only constraint (`used_in_synthesis = false`)
  because the MIG clocks do not exist during top level synthesis (the MIGs are
  synthesized out of context).
* The read data of the test engine is captured into a pipeline register before
  the 512-bit compare, which keeps the pattern generator out of the compare
  timing path.
* The `clk_external_enable` control bit (125 MHz register domain) is
  synchronized into the 64 MHz clock domain before it is used by the 1 Hz
  heartbeat counter (it was an unconstrained crossing in the `sitcp` project).
  The bit stream therefore closes timing.

## Simulation

`simulation/tb_ddr4_test_engine.v` checks the engine against a behavioural
memory model (write-data-before-command protocol, read latency, back-pressure):

```bash
cd simulation
xvlog -sv ../sources/ddr4_test_engine.v tb_ddr4_test_engine.v
xelab tb_ddr4_test_engine -s tb_engine_sim
xsim tb_engine_sim -runall
```

Covered cases: clean address-random run, injected single-word error (address,
lane and error count are checked), walking-one run, checker-board run and
abort.
